## 调研：kmp-cmp-example 的 6 个 lib-* 模块（用户问作用与可移植性）

- 结论：6 个模块源码都是**演示用薄壳**，无真实业务实现。
  - lib-base：`BaseUtils.getBaseInfo()` 返回字符串；lib-arith：`Arith.add/sub` + ohosMain `@CName("arith_createBaseUtils")`；lib-analytics/network/storage/ui：各自返回 "lib-xxx ready" 占位串。
- 真正价值在**模式演示**（6 点）：独立模块各自声明 targets/namespace；手写源集层级（iosMain/ohosMain + 禁 commonizer，因 commonizer 不认 ohos 目标）；`api(project(":lib-base"))` vs `implementation` 传递导出；`@CName` 写在**库模块的 ohosMain**（模块级导出）；`export(project(":lib-arith")){transitiveExport=}` 控制 libkn_api.h 表面（示例中为注释实验）；lib-ui 只声明 ohosArm64 演示可裁剪 targets。
- 接线：仅通过源集级依赖注入——iosMain←lib-arith；ohosMain←lib-arith/analytics/network/storage；androidMain←lib-arith；lib-ui 零引用。
- 与当前项目映射：lib-network ↔ 已有更完整的 `:core:network`；lib-base ↔ `:core:design` 角色相近；lib-storage/lib-analytics 无对应（可按需新建骨架）；lib-arith 代码无用但模式可借鉴；lib-ui 无价值。
- 纠正上一轮记录：示例 composeApp **确实**声明了 `staticLib { baseName = "kn" }`（ohosArm64+ohosX64），所以示例的 verifyHarmonyStaticLib 有效；当前项目未声明 staticLib，故我的 deployment.gradle.kts 略去该系列任务是正确的（已实测无 `linkDebugStaticOhosArm64`）。
- 当前项目 ArkTS 面：所有 @CName 都在 `composeApp/src/ohosMain/.../MainArkUIViewController.kt`（20+ 符号），无模块级导出。

## 架构对比：示例外置 lib-* vs 当前内聚 composeApp

- **当前项目做法**：真实产品代码（feature/auth/chat/home/mine…、core/router/text/ui/uuid）全在 `composeApp/src/commonMain/kotlin/com.example.my_kmp_project/` 内；`@CName` 桥接（MainArkUIViewController.kt 20+ 符号）也在 `composeApp/src/ohosMain`，直接调用同模块 feature/core。仅有 `:core:network/:core:account/:core:design` 抽成独立模块（且都非 ArkTS 面，无 @CName），通过 `implementation(projects.core.*)` 进 commonMain。
- **示例做法**：composeApp 刻意做薄（仅桥接 + 演示函数），业务以 `lib-*` 独立模块外置；composeApp 通过源集级依赖（iosMain/ohosMain/androidMain）把这些模块接进来，并用 `api`/`export` 演示符号如何进入 libkn.so。`@CName` 桥接仍在 composeApp（OhosEntry.kt 等）。
- **二者共同点**：@CName 桥接都留在 composeApp（它是产出 libkn.so 的模块）；差异在业务逻辑的归属。
- **示例把模块放外面的原因**：① 教学意图——必须把多模块边界、独立编译、api/implementation 传递导出、模块级 @CName、源集级装配这些机制显式演示出来；② 现实动机——多团队分域 ownership 的产品形态预演；③ 把 ohos 相关复杂度（禁 commonizer、手写源集）隔离在小模块里，演示更干净。
- **当前不彻底外置的原因**：单一产品/单团队，内部模块边界带来构建图开销与跨模块 API 摩擦；解耦已由自定义源集（chartsVicoMain/imageCoilMain/uuidCpfMain/networkKtorMain/accountSettingsMain/ohosMain）实现，无需模块级拆分；仅网络/账号/设计这类正交能力抽成 core:* 作为折中。
